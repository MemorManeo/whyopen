# whyopen v0.1: design

Date: 2026-08-29
Status: approved, ready for implementation planning
Follows: `2026-08-28-whyopen-design.md` (the core spec, implemented)

## 1. Problem

The core plan shipped a working auditor. Nobody can use it yet, and its
headline claim is unproven.

Three specific gaps:

- **The headline claim has never run against a real kernel.** whyopen exists
  to report that a container published on `0.0.0.0` is reachable from the
  internet even while UFW denies by default. Every test of that scenario uses
  a ruleset built by hand in Go. The development host cannot test it, because
  every publish there is correctly bound to loopback. If the claim is wrong in
  practice, the project has no reason to exist, and nothing would currently
  catch that.
- **One extension blocks a clean answer on the primary audience's hosts.** Of
  every undecoded item on a real UFW plus Docker host, only `xt recent`
  produces an `unknown` verdict: `icmp`, `icmp6`, `hl`, `rt`, `LOG`, `REJECT`
  and `MASQUERADE` are all resolved by name already. UFW's `ufw limit ssh`
  emits `recent`, so port 22, the port an operator cares about most, reports
  `unknown` on a stock UFW host.
- **There is no way to install it.** No CI, no release, no tags, no binaries.
  The audience is self-hosters, many of whom do not have a Go toolchain, and a
  large share run arm64.

## 2. Goals

1. Prove the headline claim against a real kernel and a real Docker daemon, in
   a test that runs on every change.
2. Remove the `unknown` verdicts that real hosts actually hit, deriving every
   decoder from captured bytes rather than from memory.
3. Ship installable binaries for linux amd64 and arm64.

## 3. Non-goals

Deferred to v0.2, and named here so they are not smuggled in: the policy file
and its exit codes, `--json` output, the external probe and reconciliation.
Also out of scope: decoding extensions no observed host emits, Podman,
Kubernetes, and any non-Linux platform.

## 4. Sequencing, and why

A, then B, then C.

The harness is built first because it is the instrument the decoders need.
The `xt recent` payload layout must come from real bytes: generate the rule
with `iptables -m recent` inside a namespace, read it back over netlink, and
derive the layout from what the kernel actually stored. The same instrument
answers what firewalld emits, which is currently unknown. Writing decoders
first would mean writing them from memory, which is exactly the failure mode
decision 0001 was created to avoid.

## 5. Workstream A: the validation harness

### 5.1 Shape

A separate suite behind a build tag, so `go test ./...` stays fast and
unprivileged for contributors:

```
//go:build integration && linux
```

Run as `sudo -E go test -tags integration ./test/integration/...`. Without
root, or without `ip`, `nft` or `iptables` on PATH, every test in the suite
skips with a message naming what is missing. A skip is never a pass in
disguise: the CI job asserts that the suite actually ran.

### 5.2 Namespace tests

Each test builds an isolated world and asserts verdicts against it:

1. Create a network namespace and a veth pair. The namespace side takes a
   global-scope documentation address (`203.0.113.10/24`), which is what makes
   whyopen treat it as internet-facing; `ClassifyAddr` reports TEST-NET-3 as
   global, unlike an RFC1918 address.
2. Where the case needs a container network, add a bridge inside the namespace
   holding `172.20.0.1/16`, so a DNAT target of `172.20.0.2` resolves to a
   known interface subnet and the forward path is modelled rather than
   reported unknown.
3. Apply the ruleset with `nft -f` or `iptables`, whichever the case is about.
4. Run the built binary: `ip netns exec <ns> ./whyopen collect`. Running the
   real binary rather than calling collector functions in-process avoids
   `setns` and thread-pinning entirely, and tests the path a user actually
   takes.
5. Decode the facts document and assert with `model.Evaluate`.
6. Tear the namespace down in `t.Cleanup`, including on failure.

Cases, which are the spec 10 fixtures the core plan could not capture:

- Clean UFW-shaped ruleset, default deny, one accepted port.
- `ufw-docker` rules applied, confirming a publish becomes filtered.
- A `DOCKER-USER` deny rule that overrides an otherwise-accepting DOCKER chain.
- A dead publish: a DNAT rule whose target has no listener behind it.
- An `iptables -m recent` rule, used by workstream B to capture the payload.

### 5.3 The headline test

Not in a namespace. On the CI runner:

1. Add a dummy interface carrying a global documentation address
   (`ip link add whyopen0 type dummy`, `ip addr add 203.0.113.10/32`). This is
   required: a CI runner sits behind NAT with only private addresses, and
   whyopen correctly reports `unknown` for every port on a host with no global
   address, so without this the test would assert nothing.
2. `docker run -d -p 0.0.0.0:<port>:80 <small image>`.
3. Run `whyopen check` and assert the published port is **reachable**, that the
   verdict carries a DNAT rewrite, and that the rule path contains the forward
   hook and not the input hook.
4. Remove the container and the dummy interface in cleanup.

This is the one test that proves the project's reason to exist. It is
deliberately an assertion about the whole pipeline, not about any one package.

Doing the same thing on a personally owned host would mean briefly exposing a
real port to the internet. An ephemeral CI runner makes that acceptable; a
production host does not, which is why this lives in CI.

## 6. Workstream B: decoders

### 6.1 `xt recent`

The only extension whose absence produces an `unknown` on a stock UFW host.

`ufw limit ssh` emits two rules: a `--set`, which records the source and
always matches, and a `--update --seconds 30 --hitcount 6`, which matches only
when the source has already been seen enough times. For whyopen's synthetic
packet, a first connection from a source never seen before:

- `--set` matches, and constrains nothing.
- `--update`, `--rcheck` and `--check` do not match, because the list is empty
  for that source.
- `--remove` does not match.
- An inverted match flips the above.

The struct is `xt_recent_mtinfo` (`seconds`, `hit_count`, `check_set`,
`invert`, `name[200]`, `side`), with revision 1 adding a mask. The bit values
of `check_set` are **not** asserted in this spec: workstream A generates each
variant with `iptables` and the implementation derives them from the captured
bytes, with the captured values recorded in the decision record.

The library has no decoder for this extension, so whyopen decodes the payload
itself. That is a first for this codebase and should stay contained in one
function with the layout documented beside it.

### 6.2 Native nftables expressions

Currently every native expression whyopen has no case for becomes
`ExprUnknown` and poisons the verdict, which is honest but leaves firewalld
and hand-written nft hosts reporting `unknown` widely.

This work starts with a capture, not with code: stand up firewalld in the
harness, dump its ruleset, and record which expressions it actually emits.
Decode only what that capture shows, most likely `expr.Ct`, `expr.Lookup`
(anonymous and named sets) and `expr.Range`. If the capture shows something
else, the capture wins.

A named set lookup needs the set's elements, which the collector does not
currently read. If the capture confirms named sets are common, add set
collection; if only anonymous sets appear, do not.

## 7. Workstream C: release

- `.github/workflows/ci.yml`: build, `gofmt` check, `go vet`, unit tests on
  every push and pull request.
- A second job running the integration suite with root and Docker, asserting
  the suite ran rather than skipped.
- `.goreleaser.yaml`: `CGO_ENABLED=0` static builds for linux amd64 and arm64,
  tar.gz archives, deb and rpm via nfpm, a checksums file, and a changelog
  grouped from the Conventional Commit prefixes already in use.
- `.github/workflows/release.yml` triggered on a `v*` tag.
- A `whyopen version` subcommand printing the version, commit and build date,
  injected at link time. The CLI already dispatches subcommands, so this adds
  one case rather than a new mechanism.
- Tag `v0.1.0`. Pre-1.0 signals that the facts schema and the CLI surface may
  still move, which is true: v0.2 adds `--json` and a policy file.

## 8. Testing

Unit tests stay as they are: fast, unprivileged, no build tag. The golden
fixture already covers realistic data end to end.

The integration suite is additive and gated. Its value is covering what
neither unit tests nor the fixture can: a real kernel, real netlink, real
Docker, and configurations the author does not run.

Decoder work is test-first in the usual way, with the twist that the test data
comes from the harness rather than from a hand-written literal.

## 9. Risks

- **The headline test could fail.** That is the point of writing it. If a
  container published on `0.0.0.0` is not reported reachable, the model is
  wrong and that must be found now rather than by a user.
- **GitHub runners may restrict namespace or nftables operations.** If the
  namespace suite cannot run there, the fallback is to run it in a privileged
  container in the same job. The Docker headline test is the higher-value half
  and needs no namespace at all.
- **`xt_recent_mtinfo` layout varies by revision.** Mitigated by capturing
  rather than assuming, and by refusing to decode a revision the capture did
  not cover: an unrecognised revision stays undecoded and yields `unknown`.
